## 01 · Risk score must discriminate; split tier into its own column

```
Context: React dashboard, "Entitlement register" screen. A sortable table of access-drift
findings. Currently every row renders risk score 49 and the tier badge ("T1 Auto-downgrade",
"T0 Observe") is rendered inside the same table cell as the score, under a header labeled
"Risk score".

Locate the risk-scoring function and the findings table component yourself.

Task:
1. Trace the risk score computation from source data to render. Determine whether the
   constant 49 is (a) a degenerate scoring function, (b) a hardcoded fixture value, or
   (c) a real score on unrepresentative fixture data. Report which, with the file and line.
2. If the scorer is degenerate, fix it so score varies with the inputs it claims to weigh.
   If the fixture is the problem, replace it with 8-12 findings spanning the full score
   range and all four tiers.
3. Split the tier badge out of the risk cell into its own sortable column between
   "Risk score" and "Identity".
4. Add scale context to the score: render as the number plus a band label derived from
   thresholds (e.g. "49 / 100 · elevated"). Define the band thresholds as named constants
   in one place, not inline.
5. Add a non-color visual encoding of risk: a 3-4px vertical bar or left border on the
   cell whose height/intensity is proportional to score. The numeral must remain visible —
   the bar supplements it, never replaces it.

Constraints:
- Do not change the table's column order beyond inserting the tier column.
- Band thresholds go in a single exported constant; no magic numbers in JSX.
- Sorting on "Risk score" sorts numerically on score only, never on tier.

Acceptance:
- Sorting by risk score visibly reorders rows.
- Sorting by tier is independent and produces T0→T3 (or reverse) ordering.
- Removing all color from the page still lets a reader rank rows by risk.
```

## 02 · KPI strip: fix absence-vs-zero, add denominators

```
Context: React dashboard header strip with six metrics: Drift recall, False revoke,
Mean time to revoke, Decision time, Reversibility, Sandbox cost. Each renders a value and
a caption of the form "Target <X> — measured" or "Target <X> — not yet measured".
Current values include "0m" for mean time to revoke and "—" for two unwired metrics.

Locate the KPI strip component and its data source yourself.

Task:
1. Distinguish three states explicitly in the metric model: MEASURED (has samples),
   NO_EVENTS (wired, zero qualifying events), NOT_WIRED (no instrumentation).
   Today "0m" and "—" collapse NO_EVENTS and NOT_WIRED ambiguously.
2. Render NO_EVENTS as descriptive text ("No revokes yet"), never as a zero value.
   A numeric 0 must only appear when 0 is a genuine measurement.
3. Attach sample size to every MEASURED metric. Render as value plus denominator
   (e.g. "100%" with a secondary "4 of 4"). Do not assert "measured" below a configurable
   minimum sample threshold (default 10) — below it, render the value with a
   "low sample" qualifier.
4. Give the strip hierarchy: the primary metric (drift recall) gets larger type; NOT_WIRED
   metrics render at reduced emphasis. Currently all six are visually equal weight.

Constraints:
- Do not delete the unwired metrics; de-emphasize them.
- Sample threshold is a named constant, configurable.

Acceptance:
- No metric renders "0" for a value that means "nothing happened".
- Every percentage on screen has a visible denominator.
- A metric with n=4 does not present with the same confidence as one with n=4000.
```

## 03 · Accessibility pass

```
Context: Dark-mode React dashboard (near-black background) with a data table, filter chips,
status badges, and a sidebar. Table rows each end in a button labeled "Review".

Task:
1. Color-only encoding. Find every place state is conveyed by hue alone and add a
   non-color channel (text, icon, or shape). Known instance: the green dot beside
   "GitHub capture" is the sole indicator of connection state — add a text label.
   Audit for others; the policy-tier badges encode severity in border hue only and need
   an ordered non-color cue.
2. Contrast. Compute actual contrast ratios for every text color against its real
   background. Fail anything under 4.5:1 for body text and 3:1 for large text and UI
   boundaries. Report the failing pairs with measured ratios before changing them, then
   raise the failing foregrounds to clear the floor. Prime suspects: muted secondary text
   (finding IDs, repo paths, stage sub-labels, page subtitles).
3. Accessible names. Every row's "Review" button currently exposes the identical
   accessible name. Give each one row context via aria-label or a visually hidden suffix
   including the finding ID and identity.
4. Focus. Verify a visible focus indicator exists on every interactive element (nav links,
   filter chips, sort headers, row buttons, refresh, theme toggle). Minimum 2px perimeter
   with 3:1 contrast against the adjacent background. Never remove outline without a
   compliant replacement.
5. Sort headers must expose aria-sort and be operable by keyboard.

Constraints:
- Do not change the palette's character; raise luminance of failing foregrounds only.
- Report measured ratios in your summary, not just "fixed".

Acceptance:
- Automated axe run on the page reports zero violations.
- Full keyboard traversal reaches every control with a visible focus ring.
- Screen reader announces four distinct button names, not "Review" four times.
```

## 04 · Bulk selection with undo

```
Context: React review-queue table. Each row has an individual "Review" action button.
There is no multi-select. The product advertises a "Reversibility 100%" metric.

Task:
1. Add a leading checkbox column with per-row selection and a header select-all that
   selects all rows matching the CURRENT filter, not all rows in the dataset. Label it
   accordingly and announce the count.
2. Add a sticky action bar that appears on non-empty selection, showing the selection
   count and the available bulk actions (approve, downgrade, revoke — match to whatever
   single-row actions already exist in the codebase).
3. Implement undo BEFORE implementing bulk apply. Every bulk mutation must produce a
   reversible operation record and surface a time-bounded undo affordance. If the existing
   single-row action path has no undo, build that path first and have bulk reuse it.
4. Add a row "selected" visual state. Verify it is distinguishable from hover and from
   focus, and that it does not rely on color alone.
5. Destructive bulk actions require a confirmation step that names the count and lists
   affected identities.

Constraints:
- Do not ship bulk apply in a commit that lacks undo. Split into two commits if needed:
  undo path first, bulk second.
- Selection state must survive filter changes predictably — decide and document whether
  selecting then filtering retains off-screen selections, and reflect that in the
  action bar count.

Acceptance:
- Selecting 3 rows, applying a bulk action, and pressing undo restores prior state.
- The action bar count matches what the confirmation dialog claims.
- Selected / hover / focus are three visually distinct row states.
```

## 05 · Filter chips: counts, axis separation, empty handling

```
Context: React dashboard with a single flat row of filter chips: "All findings",
"T3 Page", "T2 Broker", "T1 Auto-downgrade", "T0 Observe", "Live capture".

Task:
1. These are two independent filter axes flattened into one row: policy tier (T0-T3) and
   capture source (Live). Separate them into two labeled groups. Document and implement
   the combination semantics explicitly — OR within an axis, AND across axes.
2. Render a result count on each chip, computed from the current state of the other axis.
   Chips whose count is zero render disabled with the count visible, so the user learns
   the queue is empty for that tier without clicking.
3. Add an empty state for the table when a filter combination yields no rows: state which
   filters are active, and offer a one-click clear.
4. The active chip must be identifiable without color — add a check glyph or a
   pressed/aria-pressed state, not just the inverted fill.

Constraints:
- Counts must derive from the same single pass that produces the filtered rows. Do not
  add a separate loop per chip.

Acceptance:
- Chip counts sum consistently with the "N of M findings shown" label.
- Clicking a zero-count chip is not possible.
- Filtering to empty produces a useful screen, not a blank table body.
```

## 06 · Responsive behavior

```
Context: React dashboard. Fixed 256px sidebar with three nav links. Main content is a
four-column data table containing long repository paths and a trailing action button.
Currently designed for a ~1900px viewport.

Task:
1. Wrap the table so it never forces horizontal page scroll. Below the table's minimum
   comfortable width, either enable a scoped horizontal scroll region with visible
   affordance, or collapse rows to a stacked card layout — choose one and apply it
   consistently.
2. Collapse the sidebar below a breakpoint (icon rail or off-canvas). Three links do not
   justify 20% of a 1280px viewport.
3. Reflow the six-metric KPI strip: it must not compress to unreadable widths. Wrap to
   multiple rows rather than shrinking below a legible minimum.
4. Verify no fixed pixel container widths remain that prevent reflow, and that zoom to
   200% does not break layout or clip content.

Constraints:
- Mobile-first breakpoints. No max-width media queries layered over desktop-first rules.
- Do not disable zoom.

Acceptance:
- No horizontal page scrollbar at 375px, 768px, 1024px, 1440px.
- Table content remains reachable at every width.
- 200% browser zoom does not clip or overlap.
```

## 08 · Token architecture audit

```
Context: React dashboard, dark theme, with a light-mode toggle. A single green accent
currently appears in at least three semantically unrelated roles: the source-connection
status dot, policy-tier badge borders, and the "Live" credential badge.

Task:
1. Audit every color value in the UI layer. Report which are raw hex/rgb literals in
   components versus references to a token. List the literals with file and line.
2. Establish a three-layer token structure: primitive (raw scale values) → semantic
   (purpose aliases) → component (component-scoped). No component may reference a
   primitive directly.
3. Introduce the semantic scales this UI needs and currently lacks:
   - risk bands (low / elevated / high / critical)
   - policy tiers T0-T3, as a monotone ordered ramp, NOT arbitrary hues
   - connection/credential status (live / stale / blocked / not-wired)
   The three current uses of the same green must resolve to three distinct semantic
   tokens even if some share a primitive today.
4. Define component tokens and the full state matrix for the table row:
   default / hover / active / focus / selected / disabled. The selected and focus states
   do not currently exist and are required by the bulk-selection work.
5. Verify every semantic token resolves correctly in both themes. The light-mode toggle
   must not produce contrast failures — run the same 4.5:1 check in light mode.

Constraints:
- HSL or a format that supports opacity manipulation.
- Do not alter the perceived palette; this is a restructuring task, not a recolor. The
  tier ramp is the one permitted visual change.

Acceptance:
- Zero raw color literals in component files.
- Tier badges read as an ordered severity ramp in grayscale.
- Both themes pass the contrast floor.
```

## 09 · React render-path performance

```
Context: React (verify whether Next.js) dashboard. A filterable, sortable table currently
rendering 4 rows from a fixture, intended to scale to thousands of findings. Filter chips
and sortable column headers both mutate the visible row set. A six-metric KPI strip is
derived from the same dataset.

Task — audit and fix, reporting what you found before changing it:
1. Derived state. Filtering and sorting must be computed during render via useMemo from
   source data plus filter/sort state. If any of it runs through useEffect into setState,
   restructure — that pattern double-renders on every interaction.
2. Single pass. Combine filtering, sorting, per-chip counting, and any tier bucketing into
   one traversal. Report if the current code chains multiple .filter() calls.
3. Row components. Extract the table row into its own memoized component defined at module
   scope, never inside the table component. Pass a stable identifier and a stable handler
   reference rather than constructing a new closure per row per render.
4. Long lists. Add content-visibility: auto to rows as a first measure. Assess whether
   windowing is warranted and state the row-count threshold at which it becomes necessary.
5. Non-urgent updates. Wrap filter-chip state transitions in startTransition, or use
   useDeferredValue for the derived row list, so chip clicks stay responsive at scale.
6. Data fetching. Verify the KPI strip and the table do not independently fetch the same
   findings payload. If Next.js: fetch server-side once and pass down; minimize what
   crosses the server/client boundary.
7. Bundle. Check icon imports are per-icon, not barrel imports from the package root.

Constraints:
- Measure before and after. Report render counts for a filter-chip click with React
  DevTools Profiler or equivalent, at both the current row count and a synthetic 5000-row
  fixture.
- Do not add memo() reflexively to components that render primitives cheaply.

Acceptance:
- One filter-chip click produces one commit, not two.
- Filtering a 5000-row fixture keeps interaction under 100ms to visual feedback.
- No duplicate network fetch of the findings payload.
```
